## 2. 结论（按诚实口径分级）

- ✅ **已观察到的确定事实**：**余额会随使用下降** —— 大请求后立即 −1；此后总量由 674 降到 **662**（pack0 374→362）。此前"S1 两次小请求未见扣减"**不能**推广为"不扣积分"（属**低于可观测粒度或 0 费用模型**）。
- ⚠️ **未收口（归因不干净）**：**−12 无法逐笔归因**。可能来源：① 大请求的实际结算成本；② 实验 run 在 timeout 前**可能还发过调用**（其自述"在等结算窗口"，但实际次数未经独立核对 —— **需复核**）；③ **用户本机 WorkBuddy 桌面 App 自身在运行**（多个进程），可能同期消耗；④ 结算延迟导致的"补扣"。
- ❌ **仍不能断言**："本次这 N 个 token 被精确扣了 X credit"。要做**受控归因**需要：在**无其它用量**的窗口内，做**一次**已知规模的请求 + 前后各读一次余额（下列 §3）。

## 3. 受控归因所需（需用户再授权 1 次调用）

1. 确认用户此刻**不使用** WorkBuddy App / 其它会消耗积分的客户端（或接受这份不确定性）
2. 起 `serve`（**换一个空闲端口**，避开 8317）→ 读 credits（t0）
3. **一次**已知规模请求（例如固定 prompt + `max_tokens` 明确），记录 `usage`
4. **t0+30s** 与 **t0+15min** 各读一次 credits → 若无其它用量而差额 = 请求成本，则可**受控证明"按用量扣积分"**
5. 报告 `usage` 与 credit 差额的比值（即实际倍率）

## 4. 顺带发现的真实问题（应修）

- **默认端口 8317 与本机既有 `cli-proxy-api.exe` 冲突**（实测：`GET 127.0.0.1:8317/healthz` 返回的是 CPA 的响应，带 `X-CPA-*` 头，`/v1/workbuddy/credits` 404）。⇒ `serve` 默认端口应改为**不冲突的值**，或在端口占用时**自动挑选空闲端口**并把实际端口写进 `endpoint.json`（`endpoint.json` 机制已存在）。
- 实验 run 的 `timeout` **不是**上游/网络问题，而是**任务书里把 15/30 分钟结算等待放进了 agent 轮内**（触发了子 agent 停顿超时）。⇒ 长等待必须拆成"短采集 + 定时器续采"（本件即按此执行）。
- 探针脚本 `docs/dev/s1-billing-probe.mjs`（5KB，**不含明文凭据**，已核）为实验辅助物：入库或删除由主会话决定。
